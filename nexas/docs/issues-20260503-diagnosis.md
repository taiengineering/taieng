# diagnosis 재설계 작업 중 발견된 이슈

**날짜**: 2026-05-03
**관련 작업로그**: `nexas/docs/worklog-20260503-diagnosis-redesign.md`

## 1. 작업지시서 위치 혼동 (해결됨)

- 첫 작업지시서를 `tai-api/docs/`에 push했는데, 사용자가 taieng 레포만 보고 못 찾음.
- 당시 메모리 룰("모든 docs는 tai-api로 모음")을 따른 결과였으나, 작업 내용은 taieng 페이지였음.
- **해결**: 메모리 룰 삭제, 향후 작업지시서는 작업 대상 레포에 두는 것으로 변경.

## 2. 이미지 src 경로 불일치 (해결됨, commit 21b90f9)

- Cursor가 적용한 src: `site-assets/diagnosis-page-alert-01.png` ~ `06.png`
- 실제 Supabase 객체 경로: `site-assets/diagnosis/diagnosis1.png` ~ `diagnosis6.png`
- 사용자가 처음에 알려준 패턴과 다른 명명을 Cursor가 채택해 6장 모두 깨짐.
- **재발 방지**: 작업지시서에 정확한 URL 패턴 명시 필수.

## 3. 작업용 라벨 잔존 (해결됨, commit 714b582)

- "문제 정의 / 해결 방식 / 결과 예시 / 비교해보세요 / 이럴 때 사용하세요" 등이 작업용 구분점이었으나 production에 그대로 남음.
- 그리고 좌측 텍스트(헤드라인)가 일러스트와 무관한 일반 문구로 채워짐.
- **해결**: 라벨 전부 제거, 좌측 텍스트는 일러스트 내용에 맞는 콘티 + 설명으로 재작성.

## 4. 결정짓는 문구 누락 (해결됨, commit 714b582)

- 사용자가 처음에 가격표 위 "사고는 준비되지 않은 순간에 발생합니다 / 그래서 미리 확인해야 합니다 / 지금 상태를 모른 채 운영하는 것이 가장 위험합니다 / 법령진단은 현재 상태를 기준으로 보여줍니다" 메시지를 명시했으나 ⑧-2 통째 삭제 시 함께 사라짐.
- **해결**: 가격 섭션 직전에 `.diag-decisive` 신설 (다크 navy + 정제된 타이포).

## 5. ⑧-1 앱 프리뷰 의도 불일치 (해결됨, commit 714b582)

- TAI Safe로 이어지는 영업 동선용 섭션이었으나, diagnosis 페이지의 자체 흐름과 맞지 않다고 판단되어 사용자가 삭제 요청.
- **해결**: ⑧-1 섭션 통째 삭제, CSS도 정리.

## 6. ⑤⑥⑦ 카드 풌가로 이슈 (부분 해결)

- 일러스트 자체가 좌우 여백을 갖고 있어 카드들이 작게 보임.
- ⑤⑦은 HTML 카드로 전환해 풌가로 해결, ⑥은 사용자 요청으로 일러스트 유지.
- **잔존 사항**: ⑥의 일러스트는 다른 일러스트와 동일하게 좌우 여백이 있음. 시각적으로 ②③④과 동일 패턴이라 자연스럽지만, 카드가 풌가로로 펼쳐져 보이지는 않음. 추후 재검토 가능.

## 7. 카운트업 속도 (해결됨, commit 3c306f3)

- 첫 적용(commit fc78ff4): 1,500~2,000ms — 너무 빨라 강조 효과 약함.
- 재조정: 2,200~2,800ms로 약 40% 늘림.

## 8. footer 과다 패딩 (해결됨, commit e8cbf0f)

- footer-inner의 padding이 외부 CSS(nexas 템플릿)에서 80px+로 잡혀 patent bar 아래에 큰 빈 공간 생김.
- **해결**: footer.js의 dark theme CSS 주입에 `padding: 36px 0 32px !important` 추가. 모든 페이지에 자동 적용.

## 9. 라이브 fetch 권한 제약 (운영 이슈)

- Claude의 web_fetch가 `taieng.co.kr/service/diagnosis`에 403 반환, `.html` URL은 권한 오류.
- 이 때문에 라이브 상태 직접 확인이 불가능, GitHub 코드 기반으로만 수정.
- **우회**: 라이브 검증은 사용자가 스크린샷이나 개발자 도구 결과로 알려주는 방식으로 진행.

## 10. 200줄+ 파일 MCP 직접 수정 (룰 재검토 필요)

- 메모리 룰: "200줄+ 파일은 Cursor로, MCP 직접 수정 금지". diagnosis.html은 700줄+ 파일.
- 그러나 이번 세션에서는 변경 폭이 컸고 작업지시서 후 적용 과정에서 누락(라벨 잔존, 메시지 누락 등)이 발생했음. 이를 해결하기 위해 MCP에서 atomic full-replace로 전환.
- 결과적으로 MCP push 4회 모두 성공, 충돌 없음. atomic full-replace는 룰의 정신(부분 패치 시 SHA 충돌 위험)에서 자유로움을 확인.
- **재검토 필요**: 메모리 룰을 "부분 패치 금지, full-replace는 OK"로 명확화하거나, Cursor를 통한 일관 워크플로우 유지 여부 결정 필요.

## 11. 작업 흐름 낭비 (결과 이슈)

- "6장 이미지를 어디에 킨다"는 초기 콘티 단계에서 파악하지 못해, ⑧-2 그리드로 온개 추가 → 사용자가 의도 설명 → ⑧-2 삭제 후 본문 재구성으로 재작업.
- 초기에 이미지가 무엇을 담고 있는지 사용자에게 더 명확히 물어봤으면 우회를 줄일 수 있었음.
- **재발 방지**: 이미지/자산 제공 시 콘텐츠도 한 번에 물어 의도 확정.
