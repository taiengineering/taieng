## ⛔ 최상위 규칙 — 이 지시서는 "조사 전용"이다

1. **코드·DB·룰 데이터를 한 줄도 수정하지 않는다.** (수정은 별도 지시서로만, 대표 승인 후)
2. 원인을 찾으면 **그 자리에서 고치지 말고 멈추고 보고**한다. 자가 패치(임의 코드 결정) 절대 금지.
3. 추측으로 결론 내리지 않는다. 각 주장은 **파일/함수/라인 또는 실제 실행 중간값(증거)**을 첨부한다.
4. 법령엔진 판정 로직·Compiler·룰데이터는 GPT 영역이므로 **읽기만** 한다.
5. 조사 범위를 아래 1개 현상으로 한정한다. 다른 문제를 발견해도 수정/확장하지 말고 보고서 말미에 "추가 관찰"로만 적는다.

## 조사 절차 (각 단계의 중간값을 증거로 캡처. 추론 금지)

파이프라인 전체를 입력→결과로 따라가며, 선임 룰이 **어느 레이어에서 사라지는지**를 찾는다.
(엔진 경로: `services/diagnosis_integrated_svc.py::run_step1_via_compiler` → Compiler → rules_table)

### STEP 1 — 입력 확인 (INPUT 레이어)
- `routers/diagnosis_factory_test.py::_factory_to_step1_body`가 이 factory_id로 만든 `DiagnoseStep1Body`를 실제로 찍어라.
- 확인: sector가 MANUFACTURING으로 들어가는가? worker_count=80이 실리는가? ksic_major 등 선임 판정에 필요한 입력이 비어있지 않은가?
- 증거: 생성된 body 객체 전체(JSON).

### STEP 2 — 룰 모집단 확인 (RULE 레이어, 읽기만)
- 선임 의무 룰(산안법 15~19조)이 **현재 룰 데이터에 존재하기는 하는가?**
- 엔진이 쓰는 룰 소스(예: `master_rule_v2` 또는 Compiler가 읽는 executable_draft 계열 — 실제 소스를 코드에서 확인)에서 산안법 15~19조에 해당하는 행을 SELECT로 찾아 존재 여부·sector 분류·condition을 캡처하라.
- 분기 판정:
  - (A) 룰 자체가 없다 → RULE GAP (원인 후보)
  - (B) 룰은 있다 → STEP 3로

### STEP 3 — 어느 단계에서 탈락하는가 (APPLICABILITY / COMPILER)
- 룰이 존재한다면, Compiler 실행 중 이 선임 룰이 어디서 떨어지는지 추적:
  - sector 필터에서 탈락? (MANUFACTURING에서 제외되는가)
  - condition 평가에서 탈락? (예: worker_count 비교가 항상 false로 가는가 — 과거 `condition_1_field` 부재로 무조건 통과/탈락하던 이력 있음. 단 단정 말고 실제 값으로 확인)
  - dedup/병합에서 탈락?
- 증거: 해당 룰의 rule_id가 후보 목록에 들어왔다가 빠지는 지점의 중간 출력.

### STEP 4 — 분류
위 추적 결과로 원인을 다음 중 하나로 **분류만** 한다 (수정 금지):
ENGINE BUG / CARRIER GAP / INPUT GAP / RULE GAP / SCHEMA GAP / EXPECTED
- "EXPECTED"(정상 동작)일 가능성도 열어둘 것 — 만약 룰 데이터에 산안법 15~19조 선임 룰이 애초에 적재돼 있지 않다면, 엔진은 정상이고 데이터 공백이 원인이다.
