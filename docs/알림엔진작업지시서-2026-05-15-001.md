# 1. 작업 목적

현재 TAI 플랫폼에는 다음 구조가 혼재되어 있음.

- Legacy Notification System
- Watch Alert System
- Runtime Notification Layer

현재 목표는 단순 알림 기능 추가가 아니라:

```text
모든 엔진의 운영 이벤트를 중앙 Notification Runtime으로 수렴
```

시키는 것이다.

이번 작업은:

```text
Notification Engine Phase 1
```

구현을 목표로 한다.

---

# 2. 절대 원칙

## 원칙 1

```text
Engine은 감지한다
Notification Engine은 전달한다
```

즉:

- Watch Engine
- Workflow Engine
- Runtime Engine

등은 직접 Telegram / Slack / Email 발송 금지.

## 원칙 2

모든 엔진은 Signal/Event만 발생.

## 원칙 3

Notification Engine이:

- Queue
- Delivery
- Audit
- Escalation

을 담당.

## 원칙 4

비즈니스 로직을 Notification Engine에 넣지 않는다.

Notification은:

```text
반응 및 전달
```

만 담당.

# 5. 작업 범위

## 5.1 Event Intake 구현

Watch Engine Signal 수신 후 runtime_notification_event 생성.

필수 필드:

- event_type
- source_domain
- source_entity_id
- event_status
- severity
- source_trace
- payload
- created_at

## 5.2 Recipient Resolver 구현

지원 범위:

- operator
- owner
- manager

runtime_notification_recipient_rule 기반 rule resolution 구현.

## 5.3 Notification Queue 생성

사용 테이블:

- runtime_notification_queue

필수:

- dedupe
- cooldown
- queue 상태관리

## 5.4 Telegram Delivery Worker 구현

현재 Phase 1은 Telegram only.

구조:

```text
queue poll
→ telegram adapter
→ delivery result update
```

필수:

- retry
- fail-safe
- audit logging

## 5.5 ACK / RESOLVE 연동

기존 Watch Engine ACK 구조 유지.

연결 대상:

- runtime_notification_queue
- runtime_notification_audit

## 5.6 Audit Logging 구현

다음 항목 추적:

- 누가
- 언제
- 무엇을
- 받았고
- ACK 했는가

# 10. 성공 기준

- Watch Engine이 직접 Telegram 발송하지 않음
