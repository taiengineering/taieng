## 왜 이 문서인가 (대표 통찰)

지금까지의 executor 보정 1,951건은 **이미 분해된 의미절 데이터를 사후 교정**한 것이다.
분해기(decompose_v1.py)는 그대로라, **새 법이 들어와 분해기를 다시 돌리면 같은 executor 오류가
재발한다**(산안법 17조가 또 "지도ㆍ조언하"로 뽑힘). 즉 현재 보정은 그 법조문에만 듣는 일회성.

대표 결정: **지금 단계는 "의미절 + 보정 + LLM" 3층으로 규정(파이프라인)을 잡는다.**
보정을 데이터가 아니라 **코드(재사용 단계)**로 만들어, 새 법·개정법에 자동 적용되게 한다.

## 3층 파이프라인 (확정)

```
원문(새 법/개정법)
  │
  ▼ [1층] 의미절 분해 — decompose_v1.py (분해기, 무수정·LLM 0%)
  │      충실성·환각0·누락0 완벽. 단 executor(주어)를 못 잡는 한계.
  │      → 이 층은 GPT 영역, 진실의 기준. 절대 수정 안 함.
  ▼ [2층] 보정 — Kiwi 색출 + 규칙 (검증가능한 것만)
  │      Kiwi로 잘못된 executor 색출(명사냐 동사냐) →
  │      맨앞주어 / "A의 B" / "~의 장" / 사전등재 주체 / 나열 규칙으로 교정.
  │      BLOCKLIST(B1 법령형식어 / B2 수식절주어 / B3 사물) 차단.
  │      "완벽 2조건"(재검증 작동 ∧ 원문서 확정) 만족분만. 못 잡으면 3층으로.
  │      → 분해기 안 건드림. 격리된 후처리 단계.
  ▼ [3층] LLM — 1·2층이 못 잡은 어려운 소수
  │      조건절/수식절/생략/사물·수범자 등 규칙으로 안 되는 것.
  │      수가 작아진 뒤, 원문 대조 검증 거쳐, 코어 아닌 별도 단계 격리.
  │      생성/분해엔 LLM 배제(10장 원칙) — 여기선 "의미 판단"에만, 원문대조로 가둠.
  ▼
  최종 의미절 (executor 교정 완료)
```

## 각 층의 약점을 다음 층이 메운다 (핵심)
- 1층: 충실성 완벽, executor 못 잡음 → 2층이 메움.
- 2층: 확실한 건 완벽, 조건절·생략·수범자 못 잡음 → 3층이 메움.
- 3층: 의미판단 되나 환각 위험 → 1·2층이 수를 줄이고 원문대조로 가둠.
→ 어느 층도 혼자 완벽하지 않지만 셋을 겹치면 통제된 정확성. 통제 안 되는 행동이 생성에 안 들어감.

## 현재 위치
- 2층 보정 규칙을 회차로 개발 중(갈래1 1,951건 보정, 규칙 진화 중: 주격직결/소유격/의장/사전/blocklist).
- 아직 **코드화 안 됨** = 새 법 자동적용 소스 아직 없음. 지금은 SQL 회차로 데이터에 직접 적용 중.
- 보정 규칙이 더 굳은 뒤(나열·조사없음·갈래2·LLM 단계까지 확정) **2층을 보정 스크립트로 코드화**.
  그것이 "새 법이 오면 도는 소스".

## 코드화 시점 (대표 방침)
- 지금 즉시 코드화 ❌ — 규칙이 아직 진화 중(나열/조사없음/갈래2/LLM 미확정). 지금 굳히면 또 고침.
- 보정 규칙 안정 후 ✅ — 회차 다 돌려 규칙 확정 → 2층 전체를 하나의 보정 파이프라인 스크립트로.
  · 입력: 분해기 산출 의미절 / 출력: executor 교정된 의미절
  · 단계: Kiwi 색출 → 규칙 교정(맨앞주어/의장/사전/나열) → blocklist → 남은 것 3층(LLM)
  · 재실행 가능: 새 법 분해 후 이 스크립트만 돌리면 동일 교정.

## 작업 안전 (불변)
- 1층 분해기 무수정. 2층은 의미절 데이터/별도 스크립트에서. 3층 LLM은 격리(원문대조).
- 현재 보정은 semantic_clause_fix(임시). 원본·운영 미반영. 보정+코드화 안정 후 원본 복사·D단계.
- executor 한 단어가 수십만명 지시/패싱 좌우 → 틀린 보정보다 미룸.
