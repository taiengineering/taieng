## 0. 한눈에

오늘 핵심 한 줄: **작업자가 서명하는 안전점검이 "가짜 항목"이 아니라 "실제 항목"으로 법정 기록에 저장됨을 처음부터 끝까지 실증했고, 그 과정에서 드러난 라이브 500 세 건과 인증·로그 결함을 근본 수정했다.**

문서에 가장 크게 영향 주는 것 세 가지:
1. **작업 전 점검(inspect) 화면** — 가짜 5항목이 사라지고 서버의 실제 항목을 받는다. 배정이 없으면 "배정된 점검이 없습니다"(EMPTY)가 **정상**이다.
2. **제출이 이제 진짜로 서버에 저장된다** — 전에는 서버가 거절해도 "기기에 임시저장"에 머물렀다(무음 실패). 근본 수정됨.
3. **(예정) safe 여러 화면의 "실패해도 성공 문구"** 문제가 곧 해소된다 — 전송부 ㉮ 지시서 발행됨.

## 1. 작업자앱 ⑤ — 가짜 점검항목 차단 · 실제 저장 실증  **[완료]**

### 무엇이 문제였나
작업 전 점검(inspect) 화면이 서버에서 항목을 못 받아, **앱에 박아둔 가짜 5항목**을 보여주고 그 이름이 그대로 법정 기록(safety_inspection_results)에 저장됐다.

### 무엇이 바뀌었나
- inspect 는 이제 **`GET /work-assignments/{id}/items`** 로 서버의 실제 항목을 받는다. 가짜 생성(getDefaultItems) 제거.
- 실제 항목이 없으면 **가짜를 만들지 않고 "배정된 점검이 없습니다"(EMPTY)** 로 정직하게 표시.
- 제출 시 서버가 **참조를 검증**하고 **항목 이름을 서버 마스터로 덮어써** 위조를 차단.
- **라이브 제출까지 실증**: 실제 로그인→점검→제출 결과, 16항목 전부 참조 유효·이름 일치·가짜 무증가 확인.

### 문서 영향 (헬프센터)
- 작업 전 점검 화면 설명에서 **"항목이 없으면 빈 화면(배정된 점검이 없습니다)"은 오류가 아니라 정상 상태**임을 안내.
- "제출하면 서버에 기록된다"를 이제 **보증할 수 있다**(아래 2번과 연결).

### 한계 — 정직하게
현재 서버가 주는 점검 항목은 **어느 사업장에나 같은 범용 16종**이다(실제 법령별 항목이 아님). 즉 **"가짜 차단"은 완료**됐으나 **"작업 전 점검 콘텐츠 자체"는 아직 미완**이다. → 아래 [파킹] 참조. 문서에 "작업 전 점검 항목이 법령별로 제공된다"고 쓰면 안 된다.

## 2. 제출 무음 실패(라이브 500) 근본 수정  **[완료]**

### 문제
제출이 서버에서 500 오류가 나는데 앱은 "기기에 임시저장"만 표시했다. 사용자는 제출했다고 믿지만 **서버엔 안 온다.**

### 근본 원인 (실측)
`safety_inspections.assignment_id` 컬럼의 외래키가 `work_schedules` 를 참조하는데, 새 코드가 `work_assignments` id 를 넣어 **외래키 위반 → 500**.

### 수정
배정 id 를 일정 id 로 변환해 저장. 이제 제출이 정상 저장된다(라이브 확인).

### 문서 영향
- "제출 완료" 문구가 **실제 서버 저장을 의미**하게 됨(전엔 아님).

## 3. 라이브 500 추가 2건 수정  **[완료]**

운영 로그 접근을 복구한 뒤(아래 6번), 매분 발생하던 라이브 500 두 건을 발견·수정.

- **`/work-schedules/summary`**, **`/tbm/summary`** — 존재하지 않는 경로가 `/{id}` 라우트에 잡혀 uuid 오류(500). 이제 404 로 처리(크래시 제거).
- **원인 규명**: 이 `/{자원}/summary` 호출들은 **우리 프런트가 아니라 외부 모니터링 프로브(1분 주기)** 였다. 기능 결손 아님 — 가드로 충분.

### 문서 영향
없음(내부/모니터 이슈). 참고용 기록.

## 4. 남의 점검 열람 차단 (소유자 검증)  **[완료]**

`GET /work-assignments/{id}/items` 에 **본인에게 배정된 점검만 조회** 가능하도록 검증 추가(다르면 403). 배정 id 만으로 타인의 점검을 볼 수 없다.

### 문서 영향
- 보안 안내에 "본인에게 배정된 점검만 조회된다" 반영 가능.

## 5. 로그인 안정화 — 이메일 자가치유  **[완료]**

일부 계정이 이메일 미확인 상태라 로그인 시 **토큰이 발급되지 않아** 인증 화면이 튕기던 문제. 로그인 시 이메일을 자동 확인 처리하도록 수정(자가치유). 대부분 계정은 정상이었고(15중 14 확인), 재발 방지 목적.

### 문서 영향
- 로그인 관련 안내는 그대로. (내부 안정화)

### 문서 영향

## 7. safe 전송부 ㉮ — 착수 준비 완료  **[지시서]**

### 문제 (헬프센터가 이미 아는 그 병목)
safe.taieng.co.kr 의 전송부(`useTaiApi.ts`)가 **HTTP 실패를 삼킨다** — 400·404·409·500 이 전부 "정상 응답"처럼 반환돼, 화면마다 잘 쓰인 오류 문구가 **죽은 코드**로 남아 있었다. 그래서 "이수 처리가 완료되었습니다" 같은 문구가 **서버가 거절해도** 떴다.

### 조치
승인된 방식 **㉮(예외 전파)** 의 **실행 지시서를 발행**했다(정확한 코드 포함). Cursor 가 별도 Goal 하에 6파일 원자적으로 적용하면 된다. **(아직 미착수 — 반영되면 아래가 풀린다.)**

### 반영되면 헬프센터가 할 일 (지시서에 명시)
- `TASK-education-assign` 의 **"성공 문구는 저장됐다는 보증이 아니다" danger 경고를 제거**.
- 각 화면 문서의 **"실패와 빈 결과가 구분되지 않는다"** 안내 제거.
- 계약 대조 탈락 6화면 **재대조 대상**: 교육 이수 관리, 점검 캘린더, 작업일정, 위험성평가 목록, 평가 척도 설정, 반기 점검 증적.

**주의:** 이건 아직 **미반영**이다. 반영 완료 통지를 받은 뒤 문서를 고칠 것.

## 8. 작업자앱 계약 대조 게이트 병합  **[완료]**

작업자앱 5화면(inspect·risk·education·history·notifications)의 "화면↔서버" 어긋남을 자동 대조하는 회귀 방지 게이트(`worker-app-contract.check.mjs`)를 병합. inspect 계약은 ⑤ 반영(`/work-assignments/{id}/items`)으로 갱신. 나머지 4화면은 "수정 전 실패" 상태로 추적 — 고칠 때마다 초록으로 바뀐다. (배포·빌드 무영향.)

### 문서 영향
- 직접 없음. 다만 risk·education·history·notifications 는 **아직 계약 미충족**(서버측 결손)이라, 그 화면 문서에는 현 시점 "미완" 안내 유지.

## 10. 파킹 — 엔진 대기  **[파킹]**

- **점검 항목 마스터 진위** · **작업 전 점검 전용 템플릿**
- 구조: **법령엔진 결과 표시 → 안전관리자가 지정(선택) → 반복 점검 생성**. 현재 엔진 재작업 중이라 **의도적으로 뒤로 미뤄둔 상태**.
- 그래서 지금 실제 항목이 없어 EMPTY 가 뜨는 건 **정상적인 중간 상태**다. ⑤의 가짜 차단은 엔진이 준비될 때까지 지키는 가드레일.
- **문서 지침:** "작업 전 점검이 법령별 항목으로 완전 동작한다"고 쓰지 말 것. "가짜 기록 차단은 완료, 실제 항목 콘텐츠는 준비 중"이 현재 사실이다.
