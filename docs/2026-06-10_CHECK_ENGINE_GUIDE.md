# 체크엔진(Check Engine) — 범용 역검증 엔진 사용법

작성일: 2026-06-10
관련 파일:
- `tai-api/services/check_engine.py` (체크엔진 코어, 범용)
- `tai-api/routers/diagnosis_factory_test.py` (법령엔진용 어댑터 예시)
- `tai-api/constants/sectors.py` (sector 표준 — DB `sector_standard` 인용)

---

## 1. 왜 만들었나 (배경)

법령은 누락·오매핑이 치명적이다. LLM은 숫자 외의 문제(오매핑·누락·의미오류)를
다 잡지 못한다. 그래서 "정방향(나온 게 맞나)"과 "역방향(나와야 할 게 나왔나)"을
**항상 같이** 보는 검증이 필요하다.

역방향은 별도 기준을 사람이 정하는 게 아니라(그건 또 다른 구멍·추측이다),
**같은 룰을 결과에서 입구로 거꾸로 돌리면 된다.** 이 "거꾸로 돌리는 역할"을
하는 것이 체크엔진이다.

## 2. 핵심 개념 — 법령엔진 vs 체크엔진

| 구분 | 법령엔진 | 체크엔진 |
|------|----------|----------|
| 성격 | 특화(산업안전 법령 판정 전용) | 범용 |
| 방향 | 입력 → 룰 → 출력 | 출력 → 같은 룰 거꾸로 → 입구 대조 |
| 값 | 가짐(도메인 특화) | **없음** |
| 판단 | 함(판정) | **안 함**(사실만) |
| 데이터 | 가짐 | **없음**(계약으로 받음) |
| 오염 | 허용 안 됨(특화 유지) | 허용 안 됨(범용 유지) |

체크엔진은 **범용엔진의 4특성**을 지킨다:
1. 역할만 있다 — 대조만 한다.
2. 값을 갖지 않는다 — sector/법령/도메인 상수 하드코딩 금지.
3. 판단하지 않는다 — PASS/FAIL을 내지 않고 사실(verdict)만.
4. 데이터가 없다 — DB/테이블을 모른다. 호출부가 계약으로 넣어준다.

그리고 범용엔진의 결정적 조건: **입력과 출력은 계약(contract)으로 표준화된다.**
계약만 지키면 어떤 엔진에도 붙는다.

## 3. 계약 (입력/출력 표준)

```
입력:  items = [CheckItem(id, values[])]  +  expected(기대 기준값)
출력:  [CheckResult(id, verdict, expected, values)]

verdict:
  MATCH    : expected가 values 안에 있음        (정합)
  MISMATCH : values는 있는데 expected가 없음     (역방향 모순)
  NO_RULE  : values가 비어있음                   (룰 없음 → 판단 보류)
```

- `id` : 검사 대상 식별자. 체크엔진은 그게 무엇인지 모른다.
- `values` : 그 항목이 룰상 허용하는 값 목록. (예: 법령이 허용하는 sector들)
- `expected` : 결과가 나온 기준값. (예: 진단에 쓰인 sector)

체크엔진은 sector도 법령도 모른다. 위 계약 형식의 값만 대조한다.

## 4. 오염 제거 규칙 (다른 엔진에 붙일 때)

체크엔진을 법령엔진이 아닌 다른 엔진(문서엔진·일정엔진 등)에 쓸 때:

1. **체크엔진 코어(`check_engine.py`)는 절대 수정하지 않는다.**
   sector·법령·문서·일정 등 도메인 용어가 들어가면 그 순간 범용이 깨진다.
2. **어댑터를 새로 만든다.** 어댑터가 그 엔진의 도메인 데이터를
   계약(CheckItem)으로 변환하고, 결과(verdict)를 그 엔진 식으로 해석한다.
3. **오염(도메인 값·판단·DB접근)은 전부 어댑터에만 둔다.**

### 법령엔진용 어댑터 예시 (현재 구현)
`routers/diagnosis_factory_test.py`의 `factory_test_verify`:
- `_load_law_values_by_name()` : 법령 → 허용 sector 목록(values)을
  law_sector_mapping에서 읽어 CheckItem으로 변환 (= 어댑터의 변환부)
- `check_engine.check(items, expected=진단sector)` : 체크엔진 호출
- verdict → ok/mismatch/unmapped + sector_health(FAIL/WARN/PASS) 해석 (= 어댑터의 해석부)

법령엔진 입구 필터(`anonymous_factory_service._load_sector_allowed_draft_ids`)와
**같은 룰·같은 기준(law_id 경유, to_mapping_sector 표준)**을 쓴다. 그래서
정방향(입구 필터)과 역방향(체크엔진)이 동일한 룰을 공유한다.

## 5. 활용 방향

체크엔진은 앞으로 **엔진 표준화·완성도 향상의 소형 역검증 도구**로 쓴다.
새 엔진을 만들 때마다 그 엔진용 어댑터만 붙이면, 같은 체크엔진으로
"출력이 룰과 일관되는지"를 거꾸로 검증할 수 있다.

## 6. 주의 — 누락의 성격

체크엔진의 NO_RULE(미매핑)은 "룰이 없어 판단 보류"이지 "빠뜨려도 된다"가 아니다.
법령엔진 입구 정책상 미매핑은 **통과(가지고 감)**시키므로, 미매핑 법은
결과에서 사라지지 않고 WARN으로 추적된다. 룰(law_sector_mapping)에 값이
채워지는 만큼 체크엔진의 검증 정밀도도 함께 올라간다.

단, 룰이 없는 영역은 체크엔진도 검증하지 못한다(구멍 없는 체크의 한계).
"나와야 할 법이 애초에 안 나온" 누락은 룰 데이터가 채워져야 잡힌다.
