# WO-ENGINE-INPUT-CONTRACT-TRACE-001

**작성일**: 2026-06-20
**질문**: VR이 좁은가, 엔진이 좁은가? — 엔진 입력 계약의 실제 폭만 확정.
**금지 준수**: Check Engine/Federation/VR확장/입력화면/사용자비교/패턴읽기/1000건 없음.

## 한 줄 결론

```
엔진이 못 받는다.

(정확히: 엔진의 판정 조건이 현재 "근로자수(employee_count)" 한 차원만
 비교한다. 설비/공정/위험물/화학물질/용량/연면적을 비교하는
 구조화된 조건이 0건이다.)
```

## 판정 근거 (코드/데이터 실측)

```
엔진의 판정 조건이 비교하는 입력 차원 = "threshold_field" / "metric".
이 두 컬럼이 "엔진이 무엇을 입력으로 비교하는가"를 정의한다.

[원천 조건 테이블] appendix_condition (전체 7건):
  threshold_field 분포:
    employee_count / 명 / 7건  ← 전부
  threshold_field NULL/빈값: 0건
  → 원천 조건이 비교하는 차원 = 근로자수 단 하나.

[운영 조건 테이블] applicability_conditions (ACTIVE 14건):
  metric 분포 (직전 WO 실측):
    METRIC:EMPLOYEE_COUNT / 명 / 14건  ← 전부
  다른 metric: 0건.

→ 두 테이블 모두 일관: 엔진은 근로자수만 비교한다.
  + scope 차원으로 sector/industry(KSIC)를 본다.
  = 엔진 판정 입력 = {근로자수, 업종/sector} 2차원.
```

---

## 성공 기준 IF/THEN 적용

```
규칙:
  IF 엔진 입력 계약 = KSIC + worker_count
     THEN 엔진 입구가 2차원
  ELSE IF 엔진이 설비/공정/위험물/화학물질/용량/연면적을 받음
     THEN VR 생성기가 2차원
  ELSE UNKNOWN

판정:
  엔진 판정 조건이 비교하는 차원 = 근로자수 + KSIC(scope)
  설비/공정/위험물/화학물질/용량/연면적을 비교하는 조건 = 0건

  → IF 조건 TRUE: 엔진 입력 계약 = KSIC + worker_count

  ∴ 결론 = 엔진 입구가 2차원.
```

## 중요한 구분 (오해 방지)

```
"시설 화면에 위험물/화학물질/용량 입력란이 있다" ≠ "엔진이 그걸 쓴다".

  - 시설 등록 화면(factory-list)은 위험물/화학물질/전기용량/연면적 등을
    입력받아 factories 테이블에 저장한다. (입력은 다차원)
  - 그러나 엔진의 판정 조건(appendix_condition / applicability_conditions)이
    그 필드들을 threshold로 비교하는 룰은 0건이다.
  - 즉 엔진 입구가 데이터를 "저장"은 해도, 판정에서 "비교"하는
    차원은 근로자수+업종 2개뿐.

→ "엔진이 못 받는다" = "판정 조건이 그 차원을 안 본다"는 의미.
  (데이터 칸은 있으나 그걸 판정에 쓰는 룰이 없음)
```

## 이 결론이 정하는 방향 (사장님 IF/THEN 논리)

```
사장님 논리:
  엔진이 2차원인데 VR을 25차원으로 늘리면 의미 없음.
  엔진이 25차원 받는데 VR이 2차원이면 VR 먼저 늘려야 함.

이번 확정:
  엔진 = 2차원 (근로자수 + 업종).

→ 따라서:
  VR을 25차원으로 늘려도, 엔진이 2차원만 판정하므로
  늘린 23차원은 판정 결과를 바꾸지 못한다 (흔들 의미 없음).

  = "VR 확장"이 먼저가 아니다.
    엔진 판정 조건이 2차원인 것이 먼저다.

  ※ 단 "엔진을 늘려야 한다"는 판정/제안은 이 WO 범위 밖.
    이 WO는 "엔진이 2차원이다"라는 사실만 확정.
    (엔진 조건 확장 = 법령엔진 영역 = GPT/사장님 결정)
```
