## 0. 제품 원칙 (확정)

> **AUTO FIRST · HUMAN BY EXCEPTION**
> 정상 세금계산서 발행/수정발행은 시스템이 자동 처리한다. 관리자는 "예외"만 처리한다.
> 관리자 수동발행은 결제와 무관한 예외 경로다.

- 실제 팝빌 발행/취소는 `INVOICE_LIVE` 게이트로 잠근다. OFF면 어떤 경로든 실호출 0(423).
- 회계 판정(공급가/부가세/합계)은 항상 서버가 정본. 프론트 재계산 금지.
- 세금계산서는 공급가액 · 부가세 · 합계 3분할로 표시/저장한다.

## 1. 데이터 모델

### 1.1 tax_invoice_requests (발행요청 원장)
- 역할: 세금계산서 발행 "요청"의 수명주기 관리(요청→처리→발행/실패).
- 핵심 컬럼: `id, payment_id, company_id, source, doc_type, status, proof_type, invoicee_*(스냅샷), supply_amount, vat_amount, total_amount, supply_date, tax_invoice_id, failure_code, failure_reason, requested_at, processed_at, idempotency_key, item_name, issue_reason`
- `source` 허용값(2026-09-06 마이그레이션 후): `MYPAGE, SAAS, AUTO_PAYMENT, AUTO_SAAS, ADMIN_MANUAL`
  - `MYPAGE/SAAS` = 고객 셀프서비스(라우터에서 이 둘만 허용)
  - `AUTO_PAYMENT` = 결제성공 자동 오케스트레이터 전용(서버 내부)
  - `ADMIN_MANUAL` = 관리자 수동발행 전용(서버 내부, payment 없이 허용)
- `status` 허용값: `REQUESTED, PROCESSING, ISSUED, FAILED, REVIEW_REQUIRED, CANCELLED`
- 제약(CHECK):
  - `doc_type = 'TAX_INVOICE'` (요청 원장은 세금계산서만)
  - `proof_type = 'TAX_INVOICE'`
  - `amount_check`: `total_amount = supply_amount + vat_amount`
  - `source_check`: 위 5개 값
  - `admin_manual_payment_check`(invariant): `(source='ADMIN_MANUAL' AND payment_id IS NULL) OR (source<>'ADMIN_MANUAL' AND payment_id IS NOT NULL AND company_id IS NOT NULL)`
- 인덱스:
  - `UNIQUE(payment_id, doc_type)` — 결제 1건당 세금계산서 요청 1건(멱등)
  - `uq_tax_invoice_requests_admin_manual_idem`(partial UNIQUE): `WHERE source='ADMIN_MANUAL' AND idempotency_key IS NOT NULL` — 수동발행 더블클릭/재시도 방지

### 1.2 tax_invoices (발행 원장)
- 역할: 실제 발행된 세금계산서/현금영수증 대장(원본 ORIGINAL, 수정 MODIFIED).
- 핵심 컬럼: `id, payment_id(NULL 허용), company_id, doc_type, invoice_kind, status, mgt_key, nts_confirm_num, supply_cost, tax, total_amount, issued_at, modify_code, adjustment_reason, refund_ref, ...`
- `payment_id`는 NULL 허용 → **ADMIN_MANUAL 수동발행은 payment 없이 원장 생성**.
- `UNIQUE(doc_type, mgt_key)` — 재시도 시 중복 발행 방지.
- 원장 `status`(PENDING/ISSUED/FAILED/CANCELLED)는 요청의 `tax_status`와 별도 계약(섞지 않음).

### 1.3 doc_type 경계
- `TAX_INVOICE`와 `CASH_RECEIPT`는 상호배타. 한 결제에 둘 중 하나만.
- 모든 세금계산서 조회/집계는 `doc_type='TAX_INVOICE'` 경계 필수(현금영수증 혼입 금지).

## 2. 상태(tax_status) 라벨 계약

백엔드 값 그대로 프론트가 라벨/색으로만 매핑(프론트 재계산 금지). 미지값/null → `UNKNOWN`(fail-safe, `NONE`과 구분).

| 값 | 라벨 | 의미 |
|---|---|---|
| ISSUED | 발행완료 | 원본 발행됨 |
| MODIFIED | 수정발급 | 수정세금계산서 존재 |
| REQUESTED | 요청됨 | 발행 대기 |
| PROCESSING | 처리중 | 발행 진행 |
| FAILED | 발행실패 | 재시도 대상 |
| REVIEW_REQUIRED | 확인필요 | 관리자 확인(예외큐) |
| CANCELLED | 취소됨 | 요청 취소 |
| NONE | 미발급 | 발행 이력 없음 |
| UNKNOWN | 상태확인필요 | 조회 실패/불일치(위장 금지) |

원칙: "요청이 ISSUED니까 무조건 ISSUED"로 표기 금지. 연결된 발행 원장이 실제 ISSUED일 때만 ISSUED, 아니면 UNKNOWN.

## 3. 발행 경로(로직)

### 3.1 자동 원본(AUTO ORIGINAL) — WO-TAX-INVOICE-AUTO-01
- 트리거: 결제 성공 후처리 `services/payment_post_process.py::on_payment_success_sync` 내부(자동 이벤트 발화 직후).
- 오케스트레이터: `services/tax_auto_svc.py::maybe_auto_issue_tax_invoice(sb, payment_id, trigger, actor_id)` (얇은 helper — 새 엔진 없음).
  - 조기 NOOP: `proof_type != TAX_INVOICE` 또는 결제수단 CARD(카드매출전표가 증빙).
  - `evaluate_eligibility()` 재사용 → ALLOW만 발행 진행.
  - `create_request(source='AUTO_PAYMENT')` 로 요청 멱등 확보 → `process_tax_invoice_request()` 위임.
  - supply_date: `paid_at`의 KST 날짜만. 없거나 파싱 실패 → 예외큐(SUPPLY_DATE_UNRESOLVED), 발행 0.
- 예외큐(HUMAN BY EXCEPTION 성립 조건):
  - eligibility REVIEW_REQUIRED, 또는 자동복구 가능 DENY(`COMPANY_PROFILE_INCOMPLETE`) → `ensure_auto_exception_request()`로 `tax_invoice_requests(status=REVIEW_REQUIRED)` 기록 → admin 예외콘솔에 노출.
  - 영구 비대상 DENY(CARD/CASH/이미발행/PAYMENT_NOT_SUCCESS/REQUEST_CANCELLED) → 예외큐 미생성(큐 오염 방지).
- Fail-soft: 오케스트레이터 최상위 예외는 삼킴 → 결제/계약/알림 후처리에 영향 0.
- 멱등: `UNIQUE(payment_id, doc_type)` + create_request 활성상태 재사용 + processor guard → 중복 결제성공/고객 재클릭/재시도 시 원본 최대 1건.

### 3.2 자동 수정발행(AUTO MODIFIED) — CASE A (기존 배선 재사용)
- 트리거: 환불 확정. `services/refund_svc.py::run_refund/run_partial_refund`가 `refunds.status=DONE` 직후 `_tax_adjustment_hook(refund_id)` → `invoice_svc.process_refund_tax_adjustment(refund_id)` 호출(fail-soft).
- 규칙: 전액=수정코드 4, 부분=수정코드 2. 원본 미발행이면 수정발행 0.
- 안전: 수정발행 실패/게이트(423)가 환불 결과를 롤백하지 않음(환불 DONE 유지, 수정계산서만 FAILED/재시도).
- 이번 WO에서 코드 변경 0(테스트/freeze만).

### 3.3 고객 요청(CUSTOMER REQUEST)
- 엔드포인트: `POST /payments/{payment_id}/tax-invoice/request` (source는 MYPAGE|SAAS만 허용).
- `create_request()`로 요청 저장 후 동일 오케스트레이터로 processor까지 진행(fail-soft, 멱등). 원본 최대 1건.

### 3.4 관리자 수동발행(ADMIN MANUAL) — WO-TAX-INVOICE-MANUAL-01
- 목적: 결제와 무관한 예외 발행(사후 협의건 등)을 관리자가 직접.
- 엔드포인트(role 001):
  - `GET /payments/admin/tax-invoice-companies?q=` — 회사 검색(companies SoT, name/business_number ilike ≤20).
  - `POST /payments/admin/tax-invoices/manual` — 발행요청 생성.
    - `company_mode=EXISTING`: 서버가 companies 재조회하여 스냅샷(프론트 법적정보 불신뢰).
    - `company_mode=MANUAL`: body의 invoicee_*로 스냅샷, **companies INSERT 금지**.
    - `total_amount = supply + vat` 서버 재계산(프론트 total 미수신).
    - `idempotency_key`(uuid) partial UNIQUE로 더블클릭/재시도 방지.
    - 결과: `source=ADMIN_MANUAL, payment_id=NULL, status=REQUESTED`.
  - `POST /payments/admin/tax-invoices/manual/{request_id}/process` — 발행 processor.
    - `invoice_svc.issue_manual_tax_invoice()`(신규, `_popbill_issue_tax` seam 재사용, deterministic `mgt_key`).
    - GUARD: source=ADMIN_MANUAL, status∈{REQUESTED,FAILED}, payment_id NULL, 금액/필수필드.
    - **게이트 선행(zero-mutation)**: `INVOICE_LIVE` OFF면 request/원장 UPDATE·INSERT·provider 호출 모두 0으로 즉시 423(REQUESTED 유지).
    - 성공 → 원장(payment_id NULL, ORIGINAL, ISSUED) + 요청 ISSUED + `tax_invoice_id` 연결.
    - 실패 → 요청/원장 FAILED, 같은 `mgt_key`로 재시도(중복 발행 0).
- 프론트(admin `/tax-ops`): [예외 수동발행] 2-Tab Dialog(등록 업체 조회/직접입력) + Final Confirm 모달.

## 4. 관리자 예외 콘솔 (admin.taieng.co.kr /tax-ops)

- 화면 성격: "자동 운영 관제 · 예외 콘솔". 정상 발행은 자동, 관리자는 예외만.
- 목록: 요청일 / **소스(자동발행·고객요청·관리자 수동)** / 회사 / 사업자번호 / **공급가액·부가세·합계(3분할)** / 결제수단 / 요청상태 / 세금계산서 상태 / 발행일 / 관리.
  - ADMIN_MANUAL row는 payment 없음 → 결제수단 `-`.
- 상태별 액션(source-aware):
  - FAILED(자동/고객) → [자동발행 재시도] → `/payments/tax-invoice-requests/{id}/process`
  - 잔여 REQUESTED(자동/고객) → [자동처리 재시도]
  - **ADMIN_MANUAL + REQUESTED/FAILED → [수동발행 재시도] → `/payments/admin/tax-invoices/manual/{id}/process`** (payment processor로 흘리지 않음)
  - REVIEW_REQUIRED → [상세 확인](조회 전용)
  - ISSUED/MODIFIED/PROCESSING → 조회 전용
- 상세: 요청/결제/사업자 스냅샷(출처 표기)/원본 세금계산서/수정 이력.
  - ADMIN_MANUAL 상세는 `tax_invoice_id`로 원본 조회(payment_id 경로 미사용).
- 금액 표시: null → `-`, 실제 0 → `0원`(0원 위장 금지). 프론트 계산 0.

## 5. 안전장치(불변 계약)

- `INVOICE_LIVE` OFF → 실 팝빌 발행/취소 0. 모든 processor는 게이트를 mutation 앞에서 확인(423, zero-mutation).
- Fail-soft: 세금계산서 자동 후처리 실패가 결제/환불 성공을 롤백하지 않는다.
- 멱등: 결제 1건당 원본 1건(UNIQUE), 수동발행은 idempotency_key partial UNIQUE + deterministic mgt_key.
- 서버 SoT: 금액/증빙/사업자 스냅샷은 서버가 결정. 프론트 값 회계 판정 금지.
- doc_type 경계: 세금계산서 조회에 현금영수증 혼입 금지.
- 기존 `issue_tax_invoice`(payment 기반) 시그니처 불변 — 수동발행은 별도 신규 함수.

## 8. 남은 것 — INVOICE_LIVE 운영 릴리스 게이트 (별도, 미개시)

기능 개발은 종료. 실발행 전환은 아래 확인 후 대표 명시 승인 시에만 `INVOICE_LIVE = ON`:
- 팝빌 provider 자격/설정(공급자 정보 `TAI_CORP_NUM` 등), 실발행 안전 검증
- 자동 ORIGINAL / 자동 MODIFIED / 실패·재시도 / 멱등 라이브 리허설(가능하면 test provider)
- ON 이후 첫 실발행 모니터링 절차

게이트가 열리기 전까지 현재 상태를 그대로 유지한다.
