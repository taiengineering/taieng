## 1. SaaS 어드민 보편 구조 — "고객 360"이 1순위

여러 백오피스 가이드(Yaro Labs, Sequenzy, Taqwah, Flatlogic)가 공통으로 지목하는 최소 요건:

- **고객 360 (단일 화면 통합):** 계정·사용자 조회 시 구독상태·요금제·사용량·결제이력·미해결 문의를 여러 시스템을 오가지 않고 한 화면에서 본다. → TAI 정밀분석의 P1(고객360 부재)과 일치.
- **통제된 수정:** 요금제 변경, 크레딧 적용, 체험 연장, 계정 일시정지, 사용자 해지.
- **감사 로그(강한 합의):** 모든 쓰기 작업의 행위자·대상·이전값·새값·타임스탬프를 **어드민 라이브 전, 첫날부터 불변 기록**. "6개월 뒤 고객 분쟁이 긴급하게 만들 때는 이미 늦다." → TAI P0-3(admin_audit_logs 1건 미가동)과 일치.

**아키텍처 원칙(신규 채택):** 어드민 DB에 데이터를 복제하지 말고 **권위 있는 원천에서 읽고 기존 API로 되쓴다.** 결제=이니시스/payments, 사용량=제품 DB. TAI는 이미 `v_payments_list` 뷰를 쓰므로 이 방향이 맞다.

**첫 버전 스코프 원칙:** 엔지니어링·운영 시간을 가장 많이 쓰는 워크플로 2~3개만 잘 만들고 나머지는 후속 단계로. "이 기능이 없으면 지금 DB를 직접 뒤지거나 개발 요청을 넣는가? YES면 1차, NO면 대기." → TAI ZONE1 6화면 압축 판단의 근거.

## 2. Stripe 대시보드 = 결제 어드민 사실상 표준

TAI "결제·구독 원장" 화면 벤치마크로 최적:

- 섹션 분리: 결제 / 구독 / 인보이스 / 잔액 / **분쟁(dispute)** / 환불 / 정산.
- 결제 상세 1자리에서: 전체/부분 환불, 카드 차단·허용, 영수증 발송, 메모 추가.
- **환불 규칙(refunds 대장 설계 근거):**
  - 한 결제에 여러 번 환불 가능하나 원금 초과 불가 → **누적 환불액 컬럼 필수**.
  - 환불 시 **사유(reason) 선택 강제** → 대장에 사유·금액·처리자 기록.
- 구독: 생성·수정·일시정지·취소·예약변경이 한 섹션 → TAI 구독 수명주기 화면 기준.
- **분쟁/지불거절(신규 관점):** Stripe는 dispute를 환불과 별개 섹션으로 둔다. TAI도 카드결제 증가 시 chargeback 발생 → refunds와 별개로 "이의제기 대응" 신호를 관제 홈에 예비.

## 3. 1인 SaaS 운영 방식 — "요일별 모드"가 핵심 발견

- **진짜 적은 업무량이 아니라 컨텍스트 스위칭.** "결제 디버깅 중 화난 고객 이메일 → 지원 모드 → 서버 경보 → 운영 모드. 오후 5시면 여섯 도메인을 건드렸지만 아무것도 못 끝냄."
- **해법 = 요일별 주모드:** 월=제품(사이트 다운 아니면 지원도 안 함) / 화·수=마케팅 / 목=지원·운영(모든 티켓 응답·지표검토·문서갱신).
  - **어드민 설계 함의:** TAI ZONE 구조("ZONE1만 매일")를 요일 리듬과 결합. 목요일 지원일에 CS함·시스템로그, 평시엔 관제 홈만.
- **역할 통합:** 1인 = 개발자+마케터+CS+회계+카피+디자이너+잡역부 동시. 원칙은 "낮은 운영 오버헤드 — 기존 인프라 활용, 서드파티 API 사용, 가차없이 자동화." → TAI 이니시스·MessageMi·Gotenberg 방향과 일치.
- **한 번 만들면 수년 도는 자동화:** 비활성 재참여 메일, 플랜한도 도달 시 업그레이드 유도. → TAI: 진단완료→SaaS전환 유도, 만료임박 알림.

## 4. 한국 결제·세금 운영 — TAI 직접 적용

- **정기결제 + 전자세금계산서 자동발행:** 국내 정기결제 서비스는 반복결제 후 세금계산서 자동발행·입금정산을 한 흐름으로 묶는다(고객·상품·결제수단·청구·계산서 일괄). → TAI P0-4(계산서 발행 상태) 설계 기준선: 결제와 계산서를 한 흐름으로.
- **B2B 증빙 요건:** SaaS 구독료 비용인정에 세금계산서·카드전표 등 법정 증빙 필요. TAI 고객(사업자)의 비용처리 = 계산서 발급 필수 → 어드민에 발행상태·재발행 실무 필수. (조달청/혁신장터 진입 시 더 중요)
- **환불 접수 경로:** 전용 이메일/문의 양식으로 접수해 CRM/지원 시스템과 통합 권고 → TAI CS함 ↔ 환불처리 연결 근거.

## 5. 정밀분석 대비 검증·수정 요약

| 정밀분석 판정 | 외부사례 검증 |
|---|---|
| 고객 360 (P1) | ✅ 모든 백오피스 가이드 1순위 |
| admin_audit_logs (P0-3) | ✅ "라이브 전에 넣어라, 나중은 늦다" 강한 합의 |
| 환불 실연동 (P0-1) | ✅ Stripe 표준(부분환불 누적·사유 강제)이 refunds 대장 설계 검증 |
| 세금계산서 (P0-4) | ✅ 한국 B2B는 계산서=비용처리 필수 → 우선순위 상향 근거 |
| ZONE 구조 | ✅ 1인 "요일별 모드"와 결합 시 강화 |
| 원천 데이터 읽기 | ➕ 신규 원칙: 어드민 DB에 결제상태 복제 금지, 이니시스/payments 원천 |

**신규 추가 관점 2:**
1. **분쟁(dispute/chargeback) 대응 자리** — refunds와 별개 섹션, 관제 홈 예비 신호.
2. **원천 데이터 thin API 집계** — 고객360을 화면이 아니라 집계 레이어로 구현(뷰 활용).
