# Operational Storyline

## 목적

운영 이벤트를 단순 나열하지 않고,
원인 → 악화 → 현재 영향 → 권장 확인사항
순서의 **흐름(storyline)**으로 서술한다.

## 구조

```
1. 원인 단계 — 무엇이 시작되었는가
2. 악화 단계 — 어떻게 진행되었는가
3. 현재 영향 — 지금 어떤 상태인가
4. 권장 확인 — 무엇을 먼저 확인해야 하는가
```

## 예시

### 결제 장애 상황

```
1. 최근 응답 지연이 증가했습니다.
2. 이후 실패 흐름이 반복 발생하기 시작했습니다.
3. 현재 일부 사용자가 결제를 완료하지 못하고 있습니다.
4. 외부 API 응답 상태를 우선 확인하세요.
```

### 문서 생성 장애 상황

```
1. 문서 생성 시간이 평소보다 길어지고 있습니다.
2. 일부 요청에서 타임아웃이 발생하기 시작했습니다.
3. 현재 일부 문서가 생성되지 못하고 있습니다.
4. Gotenberg 서비스 상태를 확인하세요.
```

## 단계 매핑

| 이벤트 유형 | Storyline 단계 |
|------------|---------------|
| degradation, timeout | 1단계 (원인) |
| repeated_failure, escalation | 2단계 (악화) |
| workflow.failed, step.failed | 3단계 (현재 영향) |
| (자동 생성) | 4단계 (권장 확인) |

## 원칙

- 이벤트 나열 금지 — 반드시 흐름으로 서술
- 각 단계는 1문장
- 기술 용어 제거 (operator 프로필)
- 시간 순서 유지
- 4단계(권장 확인)는 반드시 구체적 행동
